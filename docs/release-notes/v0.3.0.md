## Summary

Talos Linux v1.14.2 (kernel 6.18.54-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades of
a Mixtile Cluster Box over its PCIe switch. Nothing has to be compiled.

**v0.3.0** is the first stable release of OpenMIOP Stack v0.3.0. Same
kernel, DTB, modules and driver source as v0.3.0-rc.1; this release
adds the hardware test with ClusterBox firmware v0.1.0-rc.6 (`omi-rc`).
Since v0.2.0-rc.1:
* **NVMe survives a Cluster Box reboot.** On Blade 3 the M.2 NVMe shares
  PERST# with the link to the Cluster Box, so a BMC reboot reset the NVMe
  under a live driver; it went `dead` ~30 s later on every blade (zpool
  suspended, DRBD lost quorum, only node reboots helped). The new
  `blade3-nvme-recover` module brings the link back and resets the NVMe
  through nvme's own reset path: back ~6 s after PERST#, no I/O errors.
* **openmiop 0.3.0:** push mode (the Cluster Box never reads a
  blade, needed for the BMC's `omi-rc` module), blades reconnect P2P
  without the Cluster Box after a fabric reset, and a peer stalled right
  after it connects is connected again after 2 s.
* `blade3-leds`: the 2.5G port LEDs light at any link speed.

Official Talos kernel and modules; U-Boot and the other extensions are
unchanged.

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.3.0/CHANGELOG.md).

## Supported hardware

Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box. The
Cluster Box BMC runs either the openmiop helper (any ClusterBox firmware
from v0.1.0-rc.1) or the `omi-rc` module:
[ClusterBox firmware v0.1.0](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.1.0)
loads it at boot. Upgrade every blade to this release **before** the BMC: the
module leaves blades without push mode alone.

## Install a new node

```sh
sha256sum -c --ignore-missing SHA256SUMS
xz -d @IMAGE@
# microSD (destroys the disk):  sudo dd if=<image>.raw of=/dev/<disk> bs=4M conv=fsync
# eMMC over USB (Maskrom):       see the README (scripts/flash-blade3-macos.sh)
```

The serial console must show
`enabling system extension openmiop 0.3.0-v1.14.2`. In maintenance mode
apply your machine configuration with the openmiop documents below,
`machine.install.disk: /dev/mmcblk0` and
`machine.install.image: @INSTALLER@`.

```yaml
machine:
  kernel:
    modules:
      - name: openmiop_ep
---
apiVersion: v1alpha1
kind: LinkAliasConfig
name: omi0
selector:
  match: link.driver == "openmiop-ep"
---
apiVersion: v1alpha1
kind: LinkConfig
name: omi0
up: true
mtu: 9000
addresses:
  - address: 10.20.0.<last octet of the management address>/24
```

Notes from the lab:
* A configuration applied to a node that booted an **older** raw image does
  not reinstall it; run `talosctl upgrade --image @INSTALLER@` on it.
* A new control-plane node cannot join etcd while the cluster lists a dead
  member (`etcdserver: unhealthy cluster`); remove that member first
  (`talosctl etcd snapshot`, then `talosctl etcd remove-member <id>`).

## Upgrade an existing node

One node at a time; mind etcd quorum.

```sh
talosctl -n <node> upgrade --image @INSTALLER@ --stage --drain=false
```

`--stage` installs on the next boot, before volumes are mounted, so the
reboot cannot hang in pod unmounts; `--drain=false` because the
client-side drain never finishes on nodes with CNPG primaries (their PDBs
allow no eviction); Talos stops the pods itself. Uncordon afterwards if a
drain had started. From v0.2.0-rc.1 nothing else changes (same machine
configuration). Mixed v0.2/v0.3 nodes work during the rollout. From
v0.3.0-rc.1 the driver is the same; the upgrade only changes the
extension version string. Rollback:
`talosctl -n <node> rollback`.

## Verification

```sh
talosctl -n <node> read /proc/cmdline          # no module.sig_enforce
talosctl -n <node> get extensions              # openmiop 0.3.0-v1.14.2
talosctl -n <node> dmesg | grep openmiop       # "peer M up, 4 queues, doorbell"; with omi-rc on the BMC: "RC push mode"
talosctl -n <node> dmesg | grep nvme           # "watching the link (up)" from blade3-nvme-recover
talosctl -n <node> get links | grep omi0       # alias omi0 on enx<mac>, up
talosctl -n <node> get addresses | grep 10.20.0
```

## Tested

Cluster Box with four Blade 3 (three control planes, one worker), a
loaded Cozystack cluster on top. All four run v0.3.0-rc.1 (same kernel,
DTB, extensions and openmiop driver source as this release); this
release build is inspected in CI (`scripts/verify-installer.sh`).

| Test | Result |
| --- | --- |
| Hot reset of the NVMe link (secondary bus reset pulse) under `dd` load | NVMe back in ~1.6 s, no I/O error, zpool ONLINE, 8 GT/s |
| Cluster Box reboots (a BMC reboot test, then the firmware rc.5 and rc.6 flashes), all four blades | NVMe back ~3-6 s after PERST# on every blade; no I/O or ZFS errors; DRBD, etcd and P2P fine |
| Cluster Box boot with `omi-rc` (firmware rc.6) | all four blades active 1.6 s after the module loads; DNS through the BMC back the same second |
| Blade reset by `nodectl` with `omi-rc` | released, link down 32 ms later, active again 14.5 s after the reset, node Ready in ~46 s |
| Blade upgrade with a peer stalled after connect | `peer N stalled, connecting again`, back in 2 s |
| iperf3 over `omi0` | 1 stream 4.3-5.1 Gbit/s on all 12 pairs (0 retransmits); 4 streams 8.1 Gbit/s; four senders at once 25.0 Gbit/s total |

## Known limitations

* One TCP flow uses one queue and one eDMA channel (~4.7 Gbit/s).
* A BMC reboot still resets every blade link for the length of its boot;
  P2P and the NVMe come back by themselves. Before this release DRBD
  9.3.4 deadlocked after BMC reboots (`__drbd_md_sync`); not seen with
  the NVMe recovery, but plan BMC updates as maintenance.
* The NVMe recovery must finish within the nvme I/O timeout (30 s); a
  link that stays down longer still leaves the NVMe dead.
* Not hardware-tested: NPU/GPU workloads (drivers load), VFIO, more than
  four blades.
