## Summary

Talos Linux v1.14.2 (kernel 6.18.54-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades of
a Mixtile Cluster Box over its PCIe switch. Nothing has to be compiled.

**v0.4.0-rc.2** is the Blade OS of OpenMIOP Stack v0.4.0-rc.2. Kernel,
DTB, U-Boot and the other extensions are the same as in v0.4.0-rc.1;
only openmiop changes:

* **Fix: a blade could lose the Cluster Box gateway under heavy load.**
  With v0.4.0-rc.1, long uploads from a blade to the LAN (BMC CPU at
  99 %) could cut the blade off the gateway for good: no LAN, internet,
  DNS or NTP over omi0 until the BMC's `omi-rc` was reloaded. Traffic
  between blades (Kubernetes, etcd, DRBD) was not affected. Cause: the
  driver measured a peer's progress between two reads of one pass while
  the TX thread also picks up credit, so a healthy peer looked stuck
  ("false stall"); 2 s later it reconnected to the BMC in a way that
  left the BMC's ring looking full forever. The same false stalls hit
  P2P peers under load.
* Gateway pull from v0.4.0-rc.1 unchanged: LAN and internet to the blade
  ~1.5x faster with ClusterBox firmware v0.2.0-rc.1 or later.

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.4.0-rc.2/CHANGELOG.md).

Inside the image: Talos v1.14.2, kernel 6.18.54-talos, the v0.3.0 DTB and
U-Boot 2026.07, and the extensions openmiop 0.4.0-rc.2 (pcie-ep-net
`@OPENMIOP_REF@`; also `blade3-nvme-recover` and `blade3-leds`), drbd,
zfs, iscsi-tools, panfrost, rockchip-rknn. `module.sig_enforce` is off
(the openmiop module is unsigned). Image references: extension
`@EXTENSION@`, overlay `@OVERLAY@`. Kubernetes is not pinned by the image
(tested with v1.34.3).

## Supported hardware

Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box. Gateway
pull needs the BMC's `omi-rc` from pcie-ep-net v0.4.0-rc.1 or later;
[ClusterBox firmware v0.2.0-rc.2](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.2.0-rc.2)
belongs to this release. Blades and BMC can be updated in either order;
the fix is in this blade release.

## Install a new node

As in [v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0#install-a-new-node),
with this release's image and `machine.install.image: @INSTALLER@`. The
serial console must show `enabling system extension openmiop 0.4.0-rc.2-v1.14.2`.

## Upgrade an existing node

One node at a time; mind etcd quorum; wait until DRBD and the databases
are healthy again before the next node.

```sh
talosctl -n <node> upgrade --image @INSTALLER@
```

* Keep the default drain (no `--drain=false`).
* Always pass `--image` and keep `machine.install.image` in the machine
  configuration equal to it; do not set
  `machine.install.grubUseUKICmdline: false`.
* Before draining a node, move CNPG primaries that archive WAL to
  SeaweedFS off it if a SeaweedFS volume server with a local volume runs
  there: draining it stops the WAL archive and the switchover hangs.
* Same machine configuration as v0.4.0-rc.1. Rollback:
  `talosctl -n <node> rollback`.

talosctl -n <node> get extensions              # openmiop 0.4.0-rc.2-v1.14.2

## Tested

Lab Cluster Box, 2026-10-13: the same driver source (test image ci-52,
openmiop 0.4.0-dev.3, pcie-ep-net 668278c) on .108, BMC on firmware
v0.2.0-rc.1 with the v0.4.0-rc.2 `omi-rc` fix loaded by hand. Stress
round: 3 parallel 300 MB blade -> LAN uploads plus a 300 MB LAN -> blade
download through the BMC (BMC CPU 99 %), then ping the BMC. This release
build is inspected in CI (`scripts/verify-installer.sh`).

| Blade driver | Result |
| --- | --- |
| 0.4.0-rc.1 (.133) | gateway lost in round 4 |
| reconnect fix only (0.4.0-dev.2, .108) | gateway lost in round 1-2 |
| **0.4.0-rc.2 source (0.4.0-dev.3, .108)** | 21 rounds, gateway up throughout; 0 stalls, 0 reconnects, 0 late drops, 0 eDMA errors; the last 15 rounds during 240 s of P2P load (iperf3 -P 4 to .204, 8.7 Gbit/s) |

Upgrade with drain and NVMe were fine.

## Known limitations

* Only .108 ran the new driver at tag time; the roll to all four blades
  follows the release.
* The BMC CPU is the gateway limit (~200 Mbit/s to a blade).
* As in v0.3.0: one TCP flow uses one queue (~4.7 Gbit/s); a BMC reboot
  resets every blade link for the length of its boot.
