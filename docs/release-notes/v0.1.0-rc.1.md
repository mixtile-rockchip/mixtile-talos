## Summary

Talos Linux v1.14.2 (kernel 6.18.54-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades
of a Mixtile Cluster Box over its internal PCIe switch. The installer image
contains the openmiop kernel module as a system extension; nothing has to
be compiled. Release candidate, part of OpenMIOP Stack v0.1.0-rc.1.

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.1.0-rc.1/CHANGELOG.md).

## Supported hardware

* Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box
* Cluster Box fabric: ASM2824 switch, links Gen3 x2; the BMC must run the
  openmiop helper ([ClusterBox firmware v0.1.0-rc.1](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.1.0-rc.1))

## What changes on a node

* Kernel argument `module.sig_enforce=1` is removed: openmiop-ep.ko is
  unsigned because Talos discards its module-signing key after each
  kernel build. The kernel is tainted by the unsigned module.
* PCIe: the Cluster Box connector (`fe150000`) runs as PCIe endpoint; the
  M.2 NVMe moves to the second PCIe3 controller (`fe160000`, PCI domain
  `0001`) and trains at 8 GT/s x2 (previously 2.5 GT/s). The PCIe SMMU is
  disabled (required for the endpoint; PCIe devices DMA without IOMMU,
  no PCIe passthrough via vfio-pci).
* Every other DTB node is unchanged from installer v0.3.2 (NPU enabled).

## Installation (new node)

```sh
sha256sum -c SHA256SUMS
xz -d metal-arm64.raw.xz
# microSD (destroys the disk):  sudo dd if=metal-arm64.raw of=/dev/<disk> bs=4M conv=fsync
# eMMC over USB (Maskrom):       ./scripts/flash-blade3-macos.sh   (see README)
```

Boot it, then apply your machine configuration with the openmiop
documents below and `machine.install.image: @INSTALLER@`.

## Upgrade an existing Talos node (one node at a time)

Mind etcd quorum on control-plane nodes.

1. Machine configuration, no reboot. Save as `omi.yaml`, one address per
   blade (10.20.0.1 is the BMC):

   ```yaml
   machine:
     kernel:
       modules:
         - name: openmiop_ep
   ---
   apiVersion: v1alpha1
   kind: LinkAliasConfig
   name: omi0
   selector:
     match: link.driver == "openmiop-ep"
   ---
   apiVersion: v1alpha1
   kind: LinkConfig
   name: omi0
   up: true
   mtu: 9000
   addresses:
     - address: 10.20.0.<last octet of the management address>/24
   ```

   ```sh
   talosctl -n <node> patch mc --mode no-reboot -p @omi.yaml
   ```

   The `LinkAliasConfig` is needed: udev names the interface `enx<mac>`.

2. Upgrade by digest:

   ```sh
   talosctl -n <node> upgrade --image @INSTALLER@
   ```

   If the drain cannot finish (pods with volumes on failed storage), add
   `--drain=false` and `kubectl uncordon <node>` afterwards. If the node
   then hangs in `unmountPodMounts`, a hardware reset from the BMC
   (`nodectl reset -n <slot>`) boots the already installed image.

Rollback: `talosctl -n <node> rollback` (previous image on the A/B boot
entries). The new DTB and U-Boot stay on disk and boot the old image.

## Verification

```sh
talosctl -n <node> version                      # Tag v1.14.2
talosctl -n <node> read /proc/cmdline           # no module.sig_enforce
talosctl -n <node> get extensions               # openmiop 0.1.0-rc.1-v1.14.2
talosctl -n <node> dmesg | grep openmiop        # link up, node N, peer M up
talosctl -n <node> get links | grep omi0        # alias omi0 on enx<mac>, up
talosctl -n <node> get addresses | grep 10.20.0
```

From a host on the fabric: `ping -c3 10.20.0.<node>` and
`ping -c3 -M do -s 8972 10.20.0.<node>` (jumbo).

## Tested configuration

Cluster Box with four Blade 3: two Debian 12 (vendor 6.1.99) and two
Talos v1.14.2 control-plane nodes, plus the BMC: five members on one
`omi0` segment. The Talos nodes ran CI build ci-6 of this repository,
which has the same kernel, DTB (`af047eb2…`), extensions and openmiop
driver source as this release; only version labels and the pinned
pcie-ep-net commit (same driver source) differ. This exact build passed
the automated image inspection in CI (`scripts/verify-installer.sh`).

**Update 2026-10-06:** this release installer
(`sha256:8f8ff824…`) was then installed with `talosctl upgrade` on both
Talos nodes (.201, .204), one at a time: etcd back (both members, with the
third member offline), kubelet healthy, no `module.sig_enforce`, openmiop
0.1.0-rc.1 loaded with all three peers up, `omi0` alias up with its
address, NVMe 8 GT/s x2, ZFS pool ONLINE, ping and 8972-byte jumbo frames
from the Debian blades and the BMC.

## Performance

| Path | TCP, 1 stream, MTU 9000 |
| --- | --- |
| Debian → Talos | 6.4-6.6 Gbit/s |
| Talos → Debian | 7.4-7.5 Gbit/s |
| Talos ↔ Talos | 6.48 / 6.73 Gbit/s |
| Debian ↔ Debian (reference) | 8.0-8.3 Gbit/s |

SHA-256 of 1 GiB Debian→Talos, 512 MiB Talos→Debian and 512 MiB
Talos→Talos transfers identical. NVMe: 8 GT/s x2, ZFS pools imported.

## Known limitations

* openmiop RX is polled; interrupt-driven RX is not implemented or tested. No multiqueue.
* Talos receives ~20 % slower than Debian (not investigated).
* BMC re-enumeration from the PCIe root port pauses fabric traffic ~1-2 s
  when a blade appears without a BAR address; a blade that crashes
  without leaving can race a BMC read and wedge the fabric until the BMC
  reboots.
* Upgrading nodes whose pods hold volumes on failed storage needs the
  drain/reset workaround above.
* Not hardware-tested: a fresh install from `metal-arm64.raw.xz`, NPU/GPU workloads (drivers load), VFIO, more
  than four blades.
